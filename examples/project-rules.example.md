# Правила проекта — пример

Скопируйте этот файл, перепишите под себя и укажите путь:

```bash
export MC_PROJECT_RULES=~/.config/multicheck/project-rules.md
```

Текст подставляется в промт всех трёх режимов. Держите свой файл **вне**
публичного репозитория: в него естественным образом попадают внутренние детали.

## Что писать

Правило работает, если по нему можно вынести вердикт, глядя в диф. Плохое
правило — «код должен быть качественным». Хорошее — «в транзакции нельзя
делать ранний выход».

Пишите то, что у вас **реально стреляло**. Список из тридцати пунктов, собранный
по книжкам, размывает внимание модели: она начнёт искать всё сразу и не найдёт
ничего. Пять-десять выстраданных правил работают лучше.

## Пример: многопользовательский веб-сервис

### Изоляция данных

- Каждая таблица с пользовательскими данными обязана иметь колонку владельца.
  Запрос без фильтра по владельцу — утечка между клиентами, даже если сейчас
  выборка кажется безопасной.
- Фоновые задачи получают идентификатор владельца явным аргументом. Брать его
  из глобального состояния нельзя: очередь исполняет задачи вперемешку.

### Транзакции

- Внутри транзакции нельзя делать ранний выход через возврат значения — только
  через исключение. Иначе транзакция закоммитится наполовину.
- Никаких сетевых вызовов и отправки писем внутри транзакции: откат уже не
  отменит отправленное письмо.

### Деньги и идемпотентность

- Любая операция списания принимает ключ идемпотентности. Повтор запроса не
  должен списывать дважды.
- Округление денег — только в одном месте. Разное округление в двух местах даёт
  расхождение, которое всплывёт через месяцы.

### Блокировки

- Блокировка без таймаута запрещена. Без него ожидание не прерывается, а
  обработчик повторов бесполезен: он не получит ошибку, которую ждёт.

### Миграции

- Одна операция изменения схемы на миграцию. Создание индекса — отдельной
  миграцией и без блокировки таблицы.
- Данные не переносятся миграцией схемы: откат схемы не откатит данные.

## Как проверить, что правила работают

Возьмите диф, в котором вы **знаете** дефект, и прогоните дважды — с правилами и
без:

```bash
mc-review старый-баг.diff                          # без правил
MC_PROJECT_RULES=./project-rules.md mc-review старый-баг.diff
```

Если находка появилась только во втором прогоне — правило сформулировано полезно.
Если не появилась ни там, ни там — правило слишком общее, переписывайте
конкретнее.
